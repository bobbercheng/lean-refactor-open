## 3. How the eight passes were run and resumed

**One line, one state root.** Every pass works on the same per-problem state root, `harness/work_fresh-a100/<problem>/`. That
directory holds:

- `state.json`: the best proof, attempts, the edit ledger, the run history and the heartbeat floor;
- `notes.md`: the model's own notes, carried over to the next pass;
- `best.lean` and the candidate and variant files.

The line ran 8 passes (1 fresh, 7 resumed). Pass 1 started fresh from the reference proofs (`--fresh`): empty per-problem state, with
the harness as described under Provenance. Passes 2–8 resumed from the state, each under its own run id, `fresh-a100-pN`. The harness
sets each problem's turn budget from that history. The trajectory headers show budgets of 6, 20, 40, 50 and 60 turns; for example,
after two flat runs a problem gets a short 6-turn polish. Before pass 4, `harness/discover.py` backfilled the line's ledger from its own
passes 1–3: 168 targeted edits and 29 dead names (`docs/a100_80_babysit.md`, 21:31). The pre-backfill states are kept as
`state.json.bak-discover-20261008-213252`.

**Per pass**, the driver `harness/replicate.sh` ran `harness/agent.py` once over all 15 problems with 4 workers. It then imported the
verified records into the bank (`bank/import_verified.py`) and re-assembled the line (`assemble/best.py`). The agent command for
passes 4–8 is in `harness/replicate.sh` and, for a resumed pass, in `infra/vast/resume_pass_instance.sh`:

```bash
python3 harness/agent.py --turns 40 --workers 4 --max-tokens 4000 --model glm-5.3-flash --reasoning-effort low --endpoint openai \
  --quant nvfp4 --work-root harness/work_fresh-a100 --run-id fresh-a100-pN $AGENT_EXTRA
# AGENT_EXTRA (infra/vast/endpoint.sh): --base-url ... --api-key-file ... --api-model glm-5.3-flash
#   --serving-tag vllm-a100-awq-w4a16 --max-api-retries 20   (+ pass 8: --relative-error-lines --variant-scores)
# --quant matters only for --endpoint openrouter; here it is ignored.
```

The trajectory headers record each pass's effective settings. Where the harness ran comes from the two run logs.

## 4. Replicating the line on 4× A100

The steps below follow the scripts as they ran for passes 6–8, with the harness on the instance. Section 7 lists the files the scripts
refer to that are not in this tree; none of them is needed for the route below.

### 4.1 Prerequisites (create your own credentials)

**Control machine** (rents, serves and watches the instance):

- **vast.ai:** an account with credit and the `vastai` CLI, configured with **your own** vast.ai API key.
- **SSH:** a key at `~/.ssh/id_ed25519`, registered with vast.ai. The scripts use this path.
- **Tools:** `python3`, `openssl`, `ssh`, `rsync`, `socat` and `curl`. `provision.sh` always starts the TLS bridge and checks it before
  it prints `READY` (§4.2), so `socat` and `curl` are required even on the on-instance route.
- **Local port 8000:** must be free. The bridge listens on `127.0.0.1:8000`.
- **systemd user session with lingering:** `provision.sh` starts the user units `lra-a100-sentry`, `lra-bridge` and `lra-health`. Run
  `loginctl enable-linger "$USER"` so they keep running after you log out.
- **vLLM bearer token:** create a random token of your own in `~/.config/vexorium/vllm_api_key`, with the directory at mode 700 and
  the file at mode 600. `create.sh`, `bootstrap.sh`, `server_up.sh` and `health.py` read it.
- **Hugging Face:** the scripts download the public checkpoint without a Hugging Face token.
- **Optional:** our GCS backup and W&B traces read `~/.config/vexorium/gcs_sync_key.json` and a W&B netrc entry. They are development
  tooling: replication does not need them, and the on-instance scripts skip them when the files are absent.
- **Executable bits:** the staged copies of most `.sh` files lost theirs. Run `chmod +x infra/vast/*.sh envs/*.sh harness/*.sh` once.
  `start_chain_instance.sh` execs `chain_on_instance.sh` directly, so the bits are needed on the instance too.
- **Checkout path:** `infra/vast/chain_a100_80.sh` hard-codes our checkout path (`/home/user/source/lean-refactor`). Edit it if
  you use the workstation layout.

**Harness host** (the A100 instance on this route):

- **CPU and disk:** `provision.sh` admits offers with at least 64 effective CPU cores and 300 GB of disk; rent with `DISK=350` (§4.2).
  It sets no RAM floor.
- **RAM:** we did not measure a floor. The memory settings:
  - each Lean compile is capped at `LRA_LEAN_MEMORY_MB` (default 16000, Lean `-M`);
  - `scorer/memgate.py` starts a compile only when available memory covers its claim (`LRA_MEMGATE_CLAIM_MB`, default 8000) plus a
    reserve (`LRA_MEMGATE_RESERVE_MB`, default 8000). Its lock and ledger live in `LRA_MEMGATE_DIR` (default `/tmp`);
  - 4 workers compiling at once can therefore reach about 64 GB, plus the 8 GB reserve, besides vLLM's own host memory.
- **Hosts we used:** our workstation ran the harness for passes 1–5 (121 GB RAM, 20 cores). The A100 hosts whose RAM is recorded had
  503 GB to 1 TB (`accounting/a100_poc.md`); the RAM of the pass 6–8 hosts is not recorded.
- **Python:** 3.12 or newer for `postpass_normalizer/probe/normalize/record_a100.py` (§4.6); every other `.py` file here also parses on
  3.11. Our local platform ran Python 3.13.9; the instance's Python version was not recorded.

**Local scoring platform and the heartbeat reference.** Local scoring ran on our workstation: Linux aarch64, 20 cores, 121 GB RAM,
Python 3.13.9. `data/reference_heartbeats_local.json` was measured there (`_measured_at` 2026-10-06T03:44:57Z, before any A100 pass).
Local scores use the ratio of a candidate's heartbeats to this file's reference value for its problem (`scorer/score.py`; the file is
written by `scorer/calibrate.py`). Passes 6–8 scored on the x86_64 instance against the same file: the H value of every record in
passes 1–8 matches it.

- **Keep the shipped file** to compare with our numbers. `assemble/best.py` uses the recorded scores and compiles nothing.
- **Rerun `python3 scorer/calibrate.py`** only if the reference proofs' heartbeats on your host differ from the file's
  `heartbeats_local` values. It compiles all 15 references and overwrites the file, so keep a copy.

### 4.2 Rent and serve

From `warmup/`:

```bash
infra/vast/search.sh                         # read-only: 4x A100 80 GB offers (bid and on-demand) and your credit
CONFIRM=yes DISK=350 infra/vast/provision.sh # rents the cheapest verified bid offer at min_bid + $0.01, then bootstrap.sh
```

**What `provision.sh` does:**

- Arms the outbid sentry at rental time (`outbid_sentry.sh` → `bid_ladder.sh`, cap `BID_CAP`, default $3.17).
- Runs `bootstrap.sh`, which:
  - waits for SSH (180 s deadline; a bad host is destroyed and replaced);
  - checks that the GPUs are free and installs nvtop as a speed probe;
  - generates the pinned TLS pair and installs `/workspace/env` and `/workspace/run_vllm.sh`;
  - downloads the 190.8 GB checkpoint, starts vLLM and waits for `server_up.sh`, which makes a real 2-token completion.
- Writes `probe/a100-instance-id`, then starts the TLS bridge (`lra-bridge`) and the health watchdog (`lra-health`).
- Prints `READY <id>` only if `server_up.sh <id> --bridge` succeeds through the bridge.
- Otherwise it prints `server up but bridge failed: instance <id> KEPT` and exits 1. On the on-instance route the bridge is not used,
  so that exit is harmless once `infra/vast/server_up.sh <id>` (without `--bridge`) prints `UP`. The instance id file is already
  written by then.

**Disk.** `DISK=350` is needed when the harness and the Lean environments live on the instance: the model takes 178 GiB and the
envs and toolchains 118 GiB (`docs/a100_80_babysit.md`, 22:20 entry). `create.sh` defaults to 300 GB, which is enough for the model
alone.

**Manual alternative:** `CONFIRM=yes DISK=350 infra/vast/create.sh <offer> <bid>`, then `infra/vast/bootstrap.sh <id>`.

**After a pre-emption,** `onstart.sh` relaunches the installed server inside the container.

### 4.3 Put the harness on the instance

`infra/vast/migrate_harness.sh` did this step for us from our GCS bucket and the Kaggle env packs. It depended on `infra/sync/`, which
is not in this tree, so it was removed (`CODE_VERSIONS.md`). The equivalent by hand, for a fresh replication that leaves our run data
behind:

```bash
ID=$(cat probe/a100-instance-id)
read -r IP PT < <(vastai show instance "$ID" --raw | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['public_ipaddr'], d['ports']['22/tcp'][0]['HostPort'])")
rsync -az -e "ssh -p $PT" --exclude '/envs/*/' --exclude '/bank/*/' --exclude probe/runs/ --exclude 'harness/work_*/' --exclude __pycache__/ ./ "root@$IP:/workspace/lra/"
ssh -p "$PT" "root@$IP" 'mkdir -p /root/.config/vexorium && chmod 700 /root/.config/vexorium'
scp -P "$PT" ~/.config/vexorium/vllm_api_key "root@$IP:/root/.config/vexorium/" && ssh -p "$PT" "root@$IP" 'chmod 600 /root/.config/vexorium/vllm_api_key'
ssh -p "$PT" "root@$IP" 'cd /workspace/lra; chmod +x infra/vast/*.sh envs/*.sh harness/*.sh; bash infra/vast/harness_setup.sh > envs_setup.out 2>&1'   # ends "SETUP DONE ok=15 failed=0"
ssh -p "$PT" "root@$IP" 'cd /workspace/lra; envs/pin_upstream.sh 4-5'   # upstream HEADs of passes 4-5; switch to 6-8 before pass 6 (4.4)
```

- **What the rsync leaves out:** the built envs and clones under `envs/` (its scripts are kept), any record directories under `bank/`,
  our run data and the line's state, and `__pycache__/`.
- **What `harness_setup.sh` builds:** the 15 Lean environments listed in `infra/vast/harness_envs.json` (Mathlib v4.25–v4.27,
  Strata, cslib, physlib and ArkLib at the pinned commits), plus ripgrep, jq, zstd and `requests`. It needs root for `apt-get`.
- **Upstream HEADs:** `harness_setup.sh` clones each project's current main. `envs/pin_upstream.sh 4-5|6-8` checks the clones out at the
  HEADs our passes saw (`CODE_VERSIONS.md`, "Upstream repositories each pass saw"). Passes 1–3 recorded none, and `4-5` is the closest.
- **Build time:** 43 minutes of wall time on the pass-6 host (`docs/a100_80_babysit.md`, 03:32).
- **Prebuilt alternative:** we also published the built x86_64 envs as public Kaggle datasets, listed in `infra/vast/envs_kaggle.tsv`
  with checksums. Their restore script is not in this tree.

**Workstation alternative** (passes 1–5's layout: the harness and Lean on your machine, the model reached through the bridge). From


These scripts make **blobless** clones, so the model's `git log -p` fetches file contents from GitHub on demand (slower, needs network).
`harness_setup.sh` makes full clones and can also run on a workstation. It needs root for `apt-get` unless ripgrep, jq and zstd are
already installed.

### 4.4 Run the passes

The harness on the instance reaches the model at `https://lra-a100:8000/v1`:

- `infra/vast/endpoint.sh` maps `lra-a100` to 127.0.0.1;
- it trusts the pinned certificate (`/workspace/tls/cert.pem`, uploaded by `bootstrap.sh`) through `REQUESTS_CA_BUNDLE`;
- it sends the key in `/root/.config/vexorium/vllm_api_key`.

To use another OpenAI-compatible server instead, set `LRA_BASE_URL`, plus `LRA_API_KEY_FILE` if that server needs a key. This is how
an organizer-run server would be used. On a workstation behind the bridge, set `LRA_BASE_URL=http://127.0.0.1:8000/v1` and
`LRA_API_KEY_FILE=$HOME/.config/vexorium/vllm_api_key`.

**Warning: keep new records apart from ours.**

- **The collision.** `harness/agent.py` appends to `probe/runs/<run-id>/verified.jsonl`, `turns.jsonl` and
  `trajectories/<problem>.jsonl`, and `--fresh` deletes `harness/work_<tag>/*/state.json`. This checkout already ships
  `probe/runs/fresh-a100-p1` … `p8`, `fresh-a100-normalize1` and `harness/work_fresh-a100`.
- **The result if you ignore it.** A rerun inside this checkout under the run ids `fresh-a100-pN` would delete the shipped line state at
  pass 1 and append its records to ours. The §4.5 assembly would then read at least 82.03, whatever the rerun scored. `bank/` only
  grows, so an import also leaks into every later assembly.
- **(a) A clean copy.** Run with no `probe/runs/fresh-a100-*`, no `harness/work_fresh-a100` and no record directories under `bank/`
  (only its `.py` files). Copy results back into a separate directory, not into this checkout. The §4.3 rsync gives the instance such a
  copy. Route (a) is required for the chain and resume scripts: `chain_on_instance.sh`, `start_chain_instance.sh`,
  `resume_pass_instance.sh` and `endpoint.sh` hard-code the tag `fresh-a100`.
- **(b) A new tag,** for example `rep-a100`. Either use the fallback loop below with `TAG=rep-a100`, or run
  `START=<first> harness/replicate.sh rep-a100 openai <last> 4`. `replicate.sh` reads `AGENT_EXTRA`, which `endpoint.sh` sets, and
  defaults to 3 workers, so pass 4 explicitly. Then assemble with `assemble/best.py --include-dev-only --only-run-prefix rep-a100-p`.

**The chain, as we ran passes 6–8, extended to all 8 passes.** On the instance, in `/workspace/lra` (a clean copy):

```bash
# after each start, wait for "chain done" in probe/a100-80-chain-instance.log before the next command
echo "--reasoning-effort default --max-tokens 6000" > AGENT_FLAGS     # passes 1-2 ran with these
setsid nohup infra/vast/start_chain_instance.sh 1 2 > /dev/null 2>&1 < /dev/null &
rm AGENT_FLAGS
setsid nohup infra/vast/start_chain_instance.sh 3 3 > /dev/null 2>&1 < /dev/null &
python3 harness/discover.py --runs fresh-a100-p1,fresh-a100-p2,fresh-a100-p3 --work-root harness/work_fresh-a100 --write   # our pre-pass-4 backfill
setsid nohup infra/vast/start_chain_instance.sh 4 5 > /dev/null 2>&1 < /dev/null &
envs/pin_upstream.sh 6-8
setsid nohup infra/vast/start_chain_instance.sh 6 7 > /dev/null 2>&1 < /dev/null &
echo "--relative-error-lines --variant-scores" > AGENT_FLAGS          # pass 8 ran with these
setsid nohup infra/vast/start_chain_instance.sh 8 8 > /dev/null 2>&1 < /dev/null &
```

**How the chain works.** `start_chain_instance.sh` runs `chain_on_instance.sh`, which:

- makes one real preflight completion;
- runs one pass at a time through `harness/replicate.sh` (tag `fresh-a100`, 4 workers);
- imports and assembles the line after every pass;
- applies the stop rules from section 3. The two-passes-under-0.3 counter starts again at each start, and a stop at ≥ 82.00 ends the
  run early.

**Settings and flags.**

- **replicate.sh's fixed settings:** every pass runs at `--turns 40 --max-tokens 4000 --reasoning-effort low`, and pass 1 adds `--fresh`.
- **Extra flags:** `endpoint.sh` appends the flags in `LRA_AGENT_FLAGS`, or else the file `AGENT_FLAGS`, after those settings.
  `argparse` keeps the last value, so `AGENT_FLAGS` overrides them for passes 1–2.
- **Scope:** the flags apply to every pass of one start, and a resume after a stop reads the same file. That is why the chain is
  started once per settings group.

The instance never releases itself. Release it from your control machine with `CONFIRM=yes infra/vast/destroy.sh <id>`.

**Fallback loop,** without the chain scripts (no preflight, no stop rules: no 82 target, no two-small-gains stop, no 79.0 check after
pass 5, no fewer-than-10-DONE check). It takes any tag:

```bash
TAG=rep-a100                      # route (b); in a clean copy (route a) fresh-a100 also works
rm -f AGENT_FLAGS; unset LRA_AGENT_FLAGS
. infra/vast/endpoint.sh          # AGENT_EXTRA: endpoint, key, model name, serving tag, retries; no per-pass flags
envs/pin_upstream.sh 4-5
for i in 1 2 3 4 5 6 7 8; do
  FRESH=""; [ "$i" = 1 ] && FRESH=--fresh
  E=low; M=4000; [ "$i" -le 2 ] && { E=default; M=6000; }
  X=""; [ "$i" = 8 ] && X="--relative-error-lines --variant-scores"
  [ "$i" = 4 ] && python3 harness/discover.py --runs "$TAG-p1,$TAG-p2,$TAG-p3" --work-root "harness/work_$TAG" --write
  [ "$i" = 6 ] && envs/pin_upstream.sh 6-8
  python3 harness/agent.py --turns 40 --workers 4 --max-tokens "$M" --model glm-5.3-flash --reasoning-effort "$E" --endpoint openai \
    --work-root "harness/work_$TAG" $FRESH --run-id "$TAG-p$i" $AGENT_EXTRA $X > "probe/$TAG-p$i.log" 2>&1
  python3 bank/import_verified.py > /dev/null
  python3 assemble/best.py --include-dev-only --only-run-prefix "$TAG-p" | head -1
done
```

**What a rerun reproduces.** Model sampling is stochastic, and the code in this tree is the pass-8 version (see `CODE_VERSIONS.md`):
for example, it builds the `UPSTREAM` digest in passes 1–3 too, which our passes 1–3 did not have. A rerun reproduces the procedure,
not the exact proofs.

**After a vast stop:**

- vast restarts only the model server.
- On the instance, run `setsid nohup infra/vast/resume_pass_instance.sh auto LAST > /dev/null 2>&1 < /dev/null &`, where `LAST` is the
  last pass of the interrupted start (2, 3, 5, 7 or 8 in the sequence above). It waits for a real model answer, finishes the cut pass
  for every problem without an `end` record, then continues the chain up to `LAST`. Leave `AGENT_FLAGS` as it was for that start.
- `infra/vast/resume_watch.sh` automated this from the control machine. It also re-arms `finalize_a100.sh`, which needs files that
  are not in this tree.

**Bring the results home:** before you destroy the instance, copy `probe/runs/fresh-a100-p*/` and `harness/work_fresh-a100/` back
into a separate directory, not into this checkout.

### 4.5 Assemble the best per problem

From `warmup/`, **in a scratch copy** (`bank/import_verified.py` writes record directories under `bank/`):

```bash
python3 bank/import_verified.py      # banks every probe/runs/*/verified.jsonl as bank/<problem>/<sha256>.json
python3 assemble/best.py --include-dev-only --only-run-prefix fresh-a100-p --out /tmp/a100_line_8203.jsonl   # passes 1-8: 82.03
python3 assemble/best.py --include-dev-only --only-run-prefix fresh-a100-  --out /tmp/a100_line_8229.jsonl   # + normalize1: 82.29
```

These commands were run in a scratch copy of this tree: `import_verified.py` imported 366 records, and the two assemblies printed
82.03 and 82.29 with the per-problem values of the §1 table. For a rerun under tag (b), use `--only-run-prefix rep-a100-p`, and see
the §4.4 warning before importing new records next to ours.

**How `assemble/best.py` chooses:**

- per problem, the record with the highest score, ties broken by fewer tokens;
- only records that compiled on the primary toolchain;
- the reference proof (33.33) when nothing beats it.

`--include-dev-only` is required because every record of this line carries provenance kind `api-dev-only` (model tag
`glm-5.3-flash-vllm-a100-awq-w4a16@openai`). The prefix `fresh-a100-p` selects passes 1–8 only. The prefix `fresh-a100-` also admits
`fresh-a100-normalize1`.

### 4.6 Normalizer post-pass

`postpass_normalizer/` is a separate small tree holding the current code: `harness/normalize.py`, the scorer it uses, and the logs.

**What it rewrites.** The rewrites are deterministic and use no model. The arena lexer counts the results as fewer tokens while Lean
elaborates the same term:

- `fun x =>` → `λx =>`
- `f (fun x => e)` → `f fun x => e`
- `f a (g x)` → `f a $ g x`
- `<|` → `$`
- `a; b` → layout

**How it checks them.** It compiles every site on the primary toolchain and drops breaking sites by bisection. The result must still
compile on every listed toolchain and score strictly higher.

To rerun it, you need the line's state, the Lean envs and Python 3.12 or newer (`record_a100.py` does not parse on 3.11). Then:

```bash
cd postpass_normalizer
cp -r ../harness/work_fresh-a100 harness/                  # the bests it starts from (a copy keeps the line's state untouched)
ln -s ../envs envs                                         # the built Lean environments
python3 harness/normalize.py --bests a100 --tag=-rerun --jobs 4 | tee probe/normalize/a100-rerun.log    # -> probe/normalize/a100-rerun.jsonl
python3 probe/normalize/record_a100.py --tag=-rerun | tee probe/normalize/record_a100-rerun.log
# -> probe/runs/fresh-a100-normalize1/verified.jsonl here; compare with ../probe/runs/fresh-a100-normalize1/, then assemble as in 4.5
```

**Notes:**

- Use a new `--tag` so the recorded files are not overwritten. Write it with `=`, because argparse would read a separate `-rerun`
  as an option.
- Every check compiles Lean, so run it on a machine with the envs and enough memory.
- `record_a100.py` stamps `harness/normalize.py@<git short sha>`. Outside a git checkout the sha comes out empty.
- `--bests a100` is the only mode that made our records. `CODE_VERSIONS.md` describes the other two.
- **Earlier runs:** the logged runs are `a100.2026-10-10.*` (2026-10-10, exploratory, not recorded: 11/15, +3.94) and `a100-v2.*`
  plus `record_a100-v2.log` (2026-10-12, recorded: 11/15, +3.93 (log; +3.94 summed from the rounded recorded scores)).

## 6. Discrepancies and caveats

- **Pass 1 alone: 68.73 (recorded at the time) versus 68.47 (from this tree).**
  - The pass-1 assembly recorded on 2026-10-07, and submitted as `sub04-a100-p1` (predicted 68.73, worker 68.70), included a 37.16
    record for `CallElimCorrect.extractedOldExprInVars` (219 tokens, provenance `fresh-a100-p1`, check 3). That record sits in our
    development bank but not in `probe/runs/fresh-a100-p1/verified.jsonl`.
  - Its proof is row 2 of `submit/candidates/sub04_a100_p1.jsonl`.
  - Without it, pass 1 alone assembles to 68.47 from this tree.
  - From pass 2 on the difference disappears, because pass 2 reached 73.58 on that problem.
- **11 vs 10 normalizer gains.**
  - The normalizer starts from the bests in the line's state (`harness/work_fresh-a100/*/state.json`). For `putnam_1995_a3` the
    state holds 93.60 (317 tokens), while pass 6 also wrote a 93.65 record (312 tokens) that the state does not hold.
  - The normalized proof scores 93.64. That beats the state best, so it counts among the 11 (+3.93 in the log; +3.94 summed from the
    rounded recorded scores), but it is below the 93.65 record the assembler picks.
  - The assembled line therefore moves on 10 problems: 82.03 → 82.29.
  - The state-based line is 82.02.
- **Partial pass summaries.** `summary.json` for passes 6 and 7 covers only the last resumed driver run, and pass 8 has none (the run
  was stopped mid-pass). The trajectories and `verified.jsonl` are complete for every pass.
- **Local scorer vs the worker.** Local scores use our heartbeat counter; the worker's can differ slightly. On the two submissions
  the difference was −0.03 each time.
- **Upstream git history in the trajectories.**
  - The harness tells the model to check the project's git history for a later simplification of the declaration.
  - Upstream commits the model read therefore appear in the trajectories. Some of them credit closed-model assistance in their own
    commit messages (passes 1–3: variational, Wick and CCS in p1; Wick, CCS and Electromagnetism in p2; CCS in p3).
  - The CCS sessions in passes 1 and 2 read upstream refactors of the target declaration.
  - This is public upstream content, kept so the trajectories stay complete.
- **Upstream HEADs moved between passes 5 and 6** (`CODE_VERSIONS.md`): the clones made on the instance for passes 6–8 were newer than
  the workstation clones of passes 4–5.
- **The harness was developed on these problems** (Provenance). Pass 1's "fresh" covers the per-problem state only.
